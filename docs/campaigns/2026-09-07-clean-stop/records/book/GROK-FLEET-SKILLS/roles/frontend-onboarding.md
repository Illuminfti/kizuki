# Frontend and onboarding worker

Read `../COMMON-WORKER.md` and the filled packet. Identify the actual product surface before selecting visual skills. Kizuki's current CLI/TUI is not evidence that a browser application exists.

Load `orient-repository`, `ux-dx-ax-parity`, `documentation-accuracy`, `elegance-review` for code/review, and `handoff-work`; add `implement-change` for code. For CLI/TUI, read the scoped package instructions and `cli-terminal-ux`. For an assigned browser UI, add `touch-and-accessibility`; load `frontend-design` only for an explicitly assigned visual design task and `vercel-react-best-practices` only for React/Next.js code. These external references must be made effectively available by root before dispatch.

1. Walk the named user journey from an empty synthetic state. Identify existing core operations, success/empty/loading/denied/degraded/error states, retry behavior, and an obvious next action.
2. Reuse the established stack and design language. Visual improvement must preserve accessibility, privacy, and the existing core policy. Fonts/assets/effects are not permission to add dependencies or network calls.
3. Keep CLI stdout/exit codes stable; test non-TTY operation and cleanup. Keep the TUI audit/undo boundary and core correction semantics. Product canon never acquires an approval queue.
4. For browser work, verify keyboard order, labels, focus restoration, visible feedback, touch access, narrow layouts, and reduced motion. Preserve legitimate security expiry semantics even when a visual timer pauses. Never persist sensitive account/record data in browser storage to hide a loading flash.
5. Exercise the public flow and inspect its rendered output using available, authorized local tooling. Record screenshots or terminal captures only with synthetic data. Explain which real-user/account/platform steps remain unrun.

A polished mock, screenshot, or automated artifact check is not unfamiliar-person acceptance.
