# Rail registry

The loop runs on rails. A rail is one scheduled job with its own period, its own
run receipt and its own line in `kizuki doctor`. Every rail is one definition in
one registry, so adding a rail is a new file and one registration line. No other
file in `packages/core/src/serve` names an extension rail. Public `RAIL_IDS`,
`DEFAULT_RAILS`, schedule seeding and readers, execution, doctor and qualification
all derive from the registered definitions. Schedule defaults remain available
from `@kizuki/core`; internal consumers import them from `serve/rail-registry.ts`.

## What a rail definition holds

`defineRail` takes these fields.

- `id`, `summary`, `period_s` and `jitter_s` describe the rail and its schedule.
- `run(context)` does one run and returns what changed. A thrown error becomes a
  failed receipt. A canon write budget that runs out becomes a stopped receipt
  named `budget:...`.
- `expects_output` says a run with work waiting must produce something. Doctor
  counts an empty streak only for such a rail, and `doctor` tells it how much work
  waits. A rail judged by staleness and failure alone sets `expects_output` to
  false and has no `doctor` probe.
- The optional fields adapt the rail to what only some rails need: `preflight`,
  `recover_canon`, `configured_period_s`, `idle_period_s`, `slot_hour`,
  `artifact` and `degrades_on_findings`.

Every execution calls `run` under the writer lease, after it has attempted canon recovery
and replayed the receipt journal. A held canon write stays visible to doctor;
new canon writes remain blocked while other work continues. The context carries
the durable write budget that every rail shares. Manual runs acquire and release
the lease; daemon runs retain the daemon's lease. A live foreign holder or another
active rail in this process prevents the callback from running.

## Adding a rail

1. Write the module with one `defineRail` export, imported from `serve/rail-definition.ts`.
2. Import it in `serve/rail-registry.ts` and add it to `EXTENSION_RAILS` under
   your slot marker.
3. Regenerate the table above. The docs test names the command.

A rail that is off until configured returns a receipt with nothing done. The loop
folds a scheduled run that did nothing into the rail's last idle receipt, so an
idle rail keeps its first receipt and a heartbeat receipt at least an hour
apart. Manual runs, once runs and rails that write an artifact always retain
their receipts. A rail that registers only in a
test uses `registerRail` from `@kizuki/core/testing`, which returns the function
that removes it again.

## Verification

- `packages/core/test/serve/rail-registry.test.ts` covers the registry, doctor,
  qualification, the writer lease, the budget, receipts and crash recovery.
- `packages/cli/test/serve/rail-registry.test.ts` runs a test-only rail through
  `kizuki serve` and `kizuki doctor`.

A process killed before receipt publication leaves no completed run receipt and
no schedule advance. After journal publication, restart replays the receipt and
its schedule transition once. This registry adds no schema migration, model
endpoint, MCP tool or canon writer. Extension modules are trusted code; captured
text cannot register a rail.
